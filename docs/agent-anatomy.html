Anatomy of an Agent

Seven words that get used interchangeably — harness, agent, tools, skills, sub agents, orchestration, Claude Code — are really two pictures: what one agent is made of, and how agents scale out.

The seven pieces

Harness
The machinery around the model: feeds context in, runs the loop, executes tool calls, enforces permissions, manages the context window. Plumbing, not intelligence. In practice: Claude Code is a harness; the Agent SDK lets you build your own.
Claude Code
One specific harness product: terminal UI, built-in tools, permission modes, plugins, MCP support. In your setup: the thing that reads your marketplace and loads its plugins.
Agent
Model + harness + tools + instructions, looping toward a goal until it's done. Not a component — the whole running system. In practice: every Claude Code session is one agent.
Tools & scripts
How the agent acts: built-ins (Read, Edit, Bash), MCP servers for external systems, and your own scripts invoked through Bash. Each call's result lands back in the context. Rule of thumb: tools change the world; their results change the context.
Skill
Packaged know-how — a SKILL.md of instructions loaded into the context on demand. It's knowledge, not execution, though it can point the model at scripts to run. In your setup: what your plugins ship (e.g. the ping skill in every acme plugin).
Sub agent
A fresh agent the main one spawns as a tool call — its own context window, its own tool set, often its own system prompt. Does the work elsewhere, returns only a report. In practice: the Agent tool; custom types defined in agents/*.md (also shipped via plugins).
Orchestration
Coordinating multiple agents into a structure: fan out readers, pipeline find→verify, plan→work→review, adversarial double-checks. In practice: the Agent tool used in parallel, Workflow scripts, or orchestrator agents like elixir-phoenix:parallel-reviewer.

Distinctions that do the work

Skill vs tool

A skill tells the model how; a tool lets it do. Skills flow into the context (amber); tools are called out of it (teal).

Agent vs harness

The harness is the engine; the agent is the whole car in motion — engine, driver (model), and cargo (context) included.

Skill vs sub agent

Both package expertise. A skill keeps the work in your context; a sub agent takes it elsewhere and sends back only the conclusion.

Sub agent vs orchestration

A sub agent is one delegate; orchestration is the management structure over many — who runs, in what order, how results merge.

Where your marketplace fits

A plugin is the shipping container for the amber and grey boxes above: skills, sub agent definitions, hooks, and MCP server configs. The marketplace (your acme repo) is the catalog that distributes plugins; the harness is what installs and loads them.

So the stack reads bottom-up: marketplace distributes plugins → plugins carry skills, agents, and tool configs → the harness loads them into every session → each session is an agent that can orchestrate more agents.
